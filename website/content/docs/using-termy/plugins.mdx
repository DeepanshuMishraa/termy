title: TypeScript plugins
description: Add custom commands and native inputs to the command palette.
---

Plugins add commands to Termy's command palette with a JSON manifest and plain TypeScript. Install [Bun](https://bun.sh/), then use **Settings → Plugins → Install from folder** to choose a plugin directory. Termy validates and copies the folder into its managed plugin directory; the same screen shows Bun status and lets you refresh, open the folder, enable, disable, or uninstall plugins.

The CLI can scaffold a plugin and install trusted source from GitHub:

```sh
termy plugin init my-plugin
termy plugin add https://github.com/example/termy-plugins --path my-plugin
termy plugin status my-plugin
termy plugin disable my-plugin
termy plugin enable my-plugin
termy plugin update my-plugin
termy plugin uninstall my-plugin
```

`add` also accepts the `install` alias, while `remove` accepts `uninstall`. GitHub repository URLs, `/tree/<ref>/<path>` URLs, `--ref`, and `--path` are supported. Termy resolves refs to full commits and stores the source metadata for predictable status and updates. Monorepos with multiple valid plugins require `--path` instead of guessing.

The installer downloads regular files as data and never clones the repository, runs its scripts, evaluates plugin code, or installs dependencies. The plugin becomes trusted Bun code when the command palette loads it, so interactive installs require confirmation and automation must pass `--yes`.

Handlers execute as normal Bun code, so they can use async functions, `fetch`, `Bun.*`, Node-compatible standard-library APIs, files, subprocesses, network requests, and local relative TypeScript imports. The action result is only the typed bridge back into Termy's native UI.

```text
plugins/hello/plugin.json
plugins/hello/plugin.ts
```

The full directory is `$XDG_CONFIG_HOME/termy/plugins` when `XDG_CONFIG_HOME` is set, `~/.config/termy/plugins` otherwise on macOS and Linux, and `%APPDATA%\termy\plugins` on Windows.

`plugin.json` owns identity and API metadata:

```json
{
  "apiVersion": 1,
  "id": "hello",
  "name": "Hello",
  "version": "1.0.0"
}
```

`version` is optional metadata shown in Settings. Set `main` to a relative TypeScript path when the entrypoint is not `plugin.ts`; it must stay inside the plugin directory and cannot be a symlink.

`plugin.ts` exports the commands without repeating manifest metadata:

```ts
export default definePlugin({
  commands: [
    {
      id: "greet",
      title: "Hello: Greet me",
      keywords: ["hello", "example"],
      icon: "info",
      inputs: [
        {
          id: "style",
          type: "select",
          label: "Greeting style",
          options: [
            { value: "short", label: "Short" },
            { value: "friendly", label: "Friendly" },
          ],
        },
        {
          id: "confirmed",
          type: "confirm",
          label: "Show greeting?",
          defaultValue: true,
        },
      ],
      async run({ inputs, context }) {
        if (inputs.confirmed !== true) return;

        const message =
          inputs.style === "friendly"
            ? `Welcome to Termy ${context.appVersion}`
            : "Hello from Termy";

        return {
          type: "toast",
          level: "success",
          message,
        };
      },
    },
  ],
} satisfies TermyPlugin);
```

Termy manages `plugins/termy.d.ts`, which supplies the global `definePlugin` function and editor types. Do not import an SDK or run a build. V1 supports local relative imports inside the plugin directory plus Bun and Node built-ins such as `bun` and `node:fs`. Package imports, out-of-root paths, and symlinks are rejected, and Termy never installs packages automatically.

## Commands and inputs

Commands support `title`, search `keywords`, `status`, `enabled`, `disabledReason`, and one of the built-in `icon` names. Inputs appear sequentially before the command runs:

- `text` provides a string with optional placeholder, default, required, and maximum length.
- `select` returns the value from a fixed options list.
- `confirm` returns a boolean.

The handler receives `inputs` plus `context`, which includes the platform and app version and may include the active working directory and command. Never interpolate free-form text directly into a shell action; map select values to fixed commands or quote values for the target shell.

## Actions

A handler can return one action, an action array, `{ actions: [...] }`, or nothing. It may also be async.

| Type | Purpose |
| --- | --- |
| `terminal.run` | Run a shell command, optionally in a working directory. |
| `termy.command` | Invoke a built-in Termy command. |
| `clipboard.write` | Copy text to the system clipboard. |
| `url.open` | Open an `http` or `https` URL. |
| `toast` | Show an info, success, warning, or error notification. |

## Bun, reloads, and trust

Termy keeps one external Bun host warm and isolates each plugin in its own Worker with execution timeouts. It resolves Bun from `TERMY_BUN_PATH`, beside the Termy executable, `PATH`, Bun's default user install, Homebrew, and `/usr/local/bin`; set `TERMY_BUN_PATH` to an absolute executable path when automatic resolution misses your installation.

Plugin content is checked whenever the command palette opens. Termy fingerprints the manifest and source tree, then bundles each changed plugin once with `Bun.build({ target: "bun" })` into `plugins/.termy-cache/bundles/<id>/<content-hash>.mjs`. Local relative imports are included in both the content hash and bundle, while unchanged plugins reuse their cached module.

Disabling a plugin keeps its managed files but removes its commands on the next command-palette refresh. Uninstalling removes Termy's managed copy and leaves the source folder you selected untouched.

The cached module is imported in a warm per-plugin Worker. Termy does not use `bun build --compile`, because a standalone executable would embed another Bun runtime for every plugin; shared `.mjs` bundles avoid that size and startup overhead. Saving a manifest or source file replaces the changed Worker and refreshes its commands without restarting Termy.

Crashes and timeouts are contained to the failed plugin Worker. Subprocesses started by plugin code can outlive that Worker, so a plugin must stop its own child processes when cancellation matters. Plugins share the persistent host transport, but if that transport exits, Termy rebuilds it and reloads the Workers on the next plugin refresh without taking down the app.

Worker isolation and import validation are not a security sandbox. Plugins are trusted local code running with your user account's file, network, and process access, so read the source before installing one.

V1 does not support plugin keybindings, custom UI, build hooks, package imports, or automatic package installation.
